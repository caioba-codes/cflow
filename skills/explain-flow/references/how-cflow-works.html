How cflow works

cflow is an agent workflow for Claude Code and Codex, built on pstack. You give the agents an idea. They plan it, build it, prove it works, review each other's work and merge it. You come in at a few clear points.

1. Prerequisites

What you need

  • Claude Code on a Claude Max plan. cflow runs several agents in parallel, so it goes through usage limits fast. More than one Max plan works best, and the subswitch skill rotates between them.
  • Codex with a ChatGPT plan (recommended). A GPT model reviews and validates the Claude agents' work. A reviewer from a second AI lab catches what the first one misses. Without it, reviews fall back to Claude.
  • GitHub and the gh CLI. Agents open, review and merge PRs there.
  • A repo where your app runs locally, plus a way for agents to drive it: Claude in Chrome or Playwright for web apps, tmux or cmux for CLIs.
  • Optional: the Claude Code Review GitHub app, an automated reviewer that comments on every PR.

Once per computer

ByouRun /setup-cflow. It detects your models, asks one budget question (pick large), shows which model does each job and asks you to confirm. Start a new chat afterwards.

Once per repo

#WhoWhat happens
CyouSay yes when cflow offers to build your repo's verify skill (or run /create-verification-skill).
DagentIt builds a script-backed skill that starts your app, drives it like a real user and captures evidence. Every later PR uses it as proof. This step pays off most.
EyouAdd one line to the repo's AGENTS.md or CLAUDE.md: "load the cflow skill first for any build, fix or plan task". Without it, /cflow applies to one message at a time.
FyouTry a small task first: /cflow add a --json flag to this command. text output stays byte-identical. verify both.

2. Step by step: one feature

The example: letting people comment on posts in your app, with a notification to the post's author. Your feature will differ, but the steps are the same. Green rows are where you decide something. The agents do the rest; open their rows only if you're curious.

Do you discuss the feature with the agent first? Not as a separate step. Your first message is the brief. The agent reads the code and runs small tests to settle what it can, then asks you only the product questions no test can answer. Want an interview first? Start with /cflow grill me first.

Idea → plan

#WhoWhat happens
1youWrite the idea in a couple of lines: "Let people comment on posts. The post's author gets notified of new comments."
agent
It plans the feature
  • It recognizes a multi-PR feature and runs the Multi-phase plan playbook. The plan is the deliverable. Nothing gets built yet.
  • Subagents read the code that matters (posts, sign-in, the database, how notifications go out).
  • Small throwaway prototypes settle every question a test can answer, like "can the app already send emails, or only in-app alerts?". Results go in the plan.
2youProduct calls. A handful of cards with options and a recommendation: "Can people edit a comment after posting?", "Notify by email or in the app only?". The agent keeps working on its recommended option meanwhile.
agent
It writes the plan
  • One section per PR (storing comments, the comment box, notifications), each with tests, a live proof and who merges it. PRs users will see are marked review-gated. Then it stops.
3youGO. The one big gate. Pick how it ships: autopilot-full (agents merge each verified PR) or autopilot-stack (they line up a verified chain and you merge it).

Plan → merged

#WhoWhat happens
agent
It builds, proves and reviews each PR
  • One agent per PR, in parallel. Each builds in small commits, tests behavior and proves the change on the running app with the verify skill.
  • Independent review. Reviewers that didn't write the code (ideally GPT) re-run the checks and the live proof and say PASS or FAIL. Green CI alone never merges anything.
4youReview-gated PRs only: approve the screenshots or video of a change users will see, like the new comment box.
agent
It merges
  • Only on PASS plus green CI.
5youDeploys and anything irreversible, like turning on emails to real users. The agent asks once, in one line, with a recommended default.

Merged → you understand it

#WhoWhat happens
agent
It explains what changed
  • When the last PR lands, it writes one explainer page with /explain-diff: background, the core idea, a code walkthrough and a 5-question quiz.
6youRead it and take the quiz. That's how you keep understanding your codebase without reading every diff.
agent
It learns from your corrections
  • Anything you correct twice becomes structure (a test, a lint rule, a type), not another note in a doc.
