How cflow works

You give AI agents an idea. They plan it, build it, test it, review each other's work and merge it. You only step in at a few points.

What you need

Claude Code with a Claude Max plan
Claude Code runs the whole flow: it plans, writes the code and tests it. Several agents run at once and use up limits fast, so more than one Max plan works best. If you have more than one, run /subswitch once and follow its setup: it installs a small tool and has you sign in to each account. After that, when an account hits its limit, it moves the agents to another one and they keep going where they stopped.
Codex with a ChatGPT Pro planrecommended
Codex is OpenAI's coding agent. cflow uses its GPT model as a second opinion: before a pull request opens, /interrogate has GPT and Claude each try to break the change separately, and it also takes a seat when cflow compares designs. A model from another lab misses different things, so together they catch more. Get Pro, the big plan: this runs on every pull request and smaller plans hit their limits fast.
Voice dictationI use Superwhisper
You'll talk your ideas through instead of typing them. I use Superwhisper; Wispr Flow, your computer's built-in dictation or anything else works too. A long, clear, in-order explanation gives the agent much more to work with than a typed line, and you get better at it with practice. Always say what "done" looks like and what proof you want to see.
GitHub
Every change lands as a pull request, so you can see, review and undo anything. Agents open, review and merge them with the gh command. Install it and run gh auth login once.
Your app, starting with one command
Agents test every change by starting your app themselves and using it the way a person would: a browser for web apps, a terminal for command-line apps. Several run at once on separate machines, so your app needs a way to start from one command. Setup step 2 teaches them how.

Set up

1
Install cflow
git clone https://github.com/caioba-codes/cflow && cflow/scripts/install.sh
2
Open Claude Code in your project and run this. Pick large, say yes when it offers to create a verification skill, then start a new chat
/setup-cflow

A verification skill is a small skill saved in your project (.claude/skills/verify-<app>/) that teaches agents to use your app like a person: how to start it, how to click or type through it, and what proves each feature works. To create it, /create-verification-skill reads your code and asks you only what the code can't answer. Then it tests the skill once on your app before handing it over.

After that, every agent checks its change by actually using your app, not just by reading the code. It pays off more than any other step. Commit it so everyone's agents share it. In your other projects, cflow offers to create one the first time you build something there.

One feature, start to finish

The featureLet people comment on posts
  1. Idea → code
  2. Step 1Talk it out← you
    Dictate the whole idea to your computer for a few minutes, start to finish: comments on posts, who can comment, what the author gets notified about. Long is fine, but keep it clear and in order, and end with what "done" means: "I can comment on a post and the author gets an email." More context gets a better result, and you get better at prompting every time.
  3. It reads your code and tests its ideas
    • /how sends subagents to read the parts that matter (posts, sign-in, the database, notifications) and explain how they work.
    • The prototype playbook runs quick throwaway experiments to answer what a test can answer, like "can the app already send email?", instead of asking you.
  4. Step 2Answer what only you can decide← you
    It settles what it can by trying it, and asks you only product calls like "Email or in-app notifications?", with options. Often there are none. There's no written plan: the code is the spec.
  5. It designs it, builds it and tests it
    • /architect sketches the types and module structure before any code, with a Claude and a GPT agent each proposing a design.
    • The feature playbook hands the code to an agent, then tests the change on your app with your verification skill. A wrong or unclear result is not a pass.
    • It splits the work into small pull requests in order: storing comments, the comment box, notifications.
    • Before each pull request opens, /interrogate has GPT and Claude separately try to break it, and /simplify and /no-comments cut dead weight.
  6. Code → merged
  7. Step 3Review and merge← you
    Each pull request says what changed and shows screenshots or a video of anything users will see, like the new comment box. Read it and merge it, or say land it and the agent merges them in order once each one passes its checks.
  8. Step 4Approve deploys and risky actions← you
    Say yes or no to deploys and anything that can't be undone, like emailing real users.
  9. Merged → you understand it
  10. It explains what it built
    • /explain-diff writes one page per finished feature: the background, how it works, a walk through the code, and a short quiz. It also reminds you of pages you haven't read yet.
  11. Step 5Read the explainer← you
    Read the one-page explainer the agent writes when the whole feature is done, and take its quiz if you want. You keep understanding your code without reading every change.
